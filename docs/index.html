课程导读：技术设计到底是什么

先搞清楚「我们在做什么」，再学「怎么做」。

一句话技术设计＝把「我们想要什么」翻译成「我们要造的东西长什么样」的一份可施工的蓝图。

你可以把它类比成盖房子：需求文档是「我要一间能住人的房子」；技术设计是「这间房有几个房间、门开在哪、水电怎么走、承重墙在哪儿、楼梯多宽」；而代码是「砖和水泥」。

蓝图画错了，砖砌得再好也白搭——所以设计阶段的每一次修改，成本远低于施工阶段的返工。

0.1 三种「设计」，别搞混

层次回答的问题主要产物谁来做本课覆盖
产品设计做什么？给谁用？解决什么问题？需求文档、原型（偏业务）、PRD产品经理 / 用户只做衔接
技术设计怎么造？数据怎么存、接口怎么定、状态怎么流转？模块划分、状态机、架构图、ER 图、OpenAPI、设计文档架构师 / 技术负责人 / 开发本课主体
详细设计这段代码具体怎么写？函数签名、类图、算法伪码、单元测试用例开发本人只做衔接
一个常见误会

「我先写完，再补设计文档」——这是学生项目最常见的翻车姿势。设计不是写给甲方看的 PPT，而是写给自己看的：当你三个月后忘了当初为什么把订单拆成三个状态时，这份文档就是你的记忆外挂。

0.2 为什么值得花时间做设计

❌ 不做设计的代价
  • 需求一变，牵一发动全身
  • 两个人写的模块互相踩代码
  • 表结构和接口对不上，联调天天吵
  • 最后没人知道「为什么当初这么设计」
✓ 做设计的收益
  • 改动影响面一眼看清
  • 并行开发有共同依据
  • 测试用例从设计里直接长出来
  • 换人接手成本骤降

0.3 本课全景：八个模块的「血缘图」

这八个模块不是并列的八个坑，而是一条有方向的流水线。上游的产出是下游的输入，下游发现上游的问题时要回头改上游——这就是第 7 章要讲的「一致性核对」。

记住这句

需求 → 功能模块 → 业务流程/状态机 → UI 原型 → 架构 → 数据模型 → API 契约 → 一致性核对 → 设计文档

这条链上任何一环动了，都要回头检查它上游和下游 impacted 的部分。第 7 章会给你一张可以打印的核对矩阵。

0.4 这门课在 AI 时代更值钱的原因

坦率地说：写出「能跑的代码」正在贬值。大模型几秒钟就能生成一个 CRUD、画一个页面、搭一个脚手架。真正稀缺的是什么？

能力AI 接手后的状况你还要不要练
写出样板代码AI 秒级完成，质量已可用不必再练手速，改练审阅
画一个 UI 稿AI 能出图，但常不符合你的业务约束练约束表达与验收标准
把模糊需求问清楚AI 只会帮你把模糊需求更流畅地模糊掉必须练，这是你的护城河
做技术取舍并承担后果AI 可以列选项，但拍板与担责是你必须练
写出无歧义、可验证的规格AI 输出的质量 ＝ 你输入的精度必须练，本课就是练这个

本课的一个隐含主张

第 10 章会专门展开。这里先给你结论：在 AI 时代，「设计」不是流程负担，而是最高杠杆的一步。 给 AI 一句「帮我写个订单模块」，你得到的是千篇一律的电商模板；给它一份包含状态机、错误码、边界条件、验收标准的规格，你得到的才是能上线的代码。 所以本课的八个模块，恰好就是把「书接力的订单要支持取消」这种模糊句子，逐步升级成「状态 PAID 下收到 event=APPLY_REFUND 且 refundable=true 时迁移到 REFUNDING，同时写审计日志并释放库存锁」这种可执行规格的八个台阶。

0.5 贯穿案例：书接力（BookRelay）

整本教案用同一个例子讲到底，这样每一章都能看到「上一章的成果如何变成这一章的输入」。

项目背景

书接力是一个校园二手教材流转平台：学生把闲置教材挂上去，别人下单后线下交接，双方互评。 目标是让二手教材在校园里转起来，减少浪费。

用户角色：学生（买家/卖家）、管理员 核心对象：书籍、订单、评价、消息 规模假设：单校 2 万人，峰值 200 并发，日订单 300 单 约束条件：学生开发者 3 人、3 个月工期、预算 0（用免费层云服务）

请记住上面这行「约束条件」——它是第 4 章技术选型的直接输入。很多同学做设计时忘了自己只有 3 个人 3 个月，一上来就要微服务，那是要交学费的。

学习建议

每学完一章，就打开你的课程项目（哪怕是个很小的东西），按该章的产出物清单做一遍。看懂了 ≠ 会做。本课每个模块末尾都有「动手任务」，第 9 章会把八步串成一次完整实战。

01

功能模块设计：把系统切成「职责清晰」的块

解决一个问题：这么大一个系统，谁负责哪一块？

一句话功能模块设计＝把系统按「业务职责」切成若干块，每块有明确的名字、明确的职责、明确的对外接口。

像给一栋楼分区：宿舍楼、食堂、图书馆、实验楼。分区不是为了好看，而是为了让「快递来了放哪儿」「水管爆了找谁修」这类问题有明确答案。

1.1 为什么不能「不分模块」

把所有功能塞进一个巨大模块，会出现三个必然结果：

  • 谁都能改，改什么都可能崩——改一个按钮把下单功能搞挂了，因为它们共用同一段代码。
  • 没法分工——3 个同学 3 个模块，才能并行开发；都改同一个模块只能排队。
  • 没法复用——「发通知」写在了下单逻辑里，下次「评价通知」又要抄一遍。

1.2 两种切法，别混用

业务模块（功能域视角）

按「业务在做什么」切：用户、商品、订单、支付、评价、通知、后台管理。

这是本章要讲的。它的产出叫「功能模块说明书」，和需求文档、技术架构直接对应。

技术分层（架构视角）

按「代码在哪个层」切：Controller / Service / Repository / UI。

这是第 4 章架构设计的内容。两者不是替代关系，而是两个维度：业务模块回答「系统能干什么」，技术分层回答「代码怎么摆」。

经典错误

把「用户管理」「商品管理」当业务模块，等于把数据库的表名直接抄了一遍——它只说明了数据，没有说明业务。业务模块应该体现「用户在这个系统里做什么事」，比如「买家」「卖家」其实比「用户管理」更有信息量，因为它们的行为和权限完全不同。

1.3 五步拆解法

  1. 第一步：撒网列候选
    把需求里所有「动词 + 名词」捞出来。如：登录、浏览书籍、发布书籍、下单、支付、取消、评价、通知、审核。不用管重复，先全列出来。
  2. 第二步：按业务对象聚类
    把功能挂到它操作的「东西」上：都跟书籍有关的 → 书籍域；都跟订单有关的 → 订单域。聚类时会自然暴露出重复和不清晰的地方。
  3. 第三步：写清每个模块的一句话职责
    检验标准：这句话里不出现「和」「以及」「等」这种含糊词。「负责用户相关功能」不合格，「负责用户注册、登录与身份凭证管理」合格。
  4. 第四步：划边界（依赖与对外能力）
    写清楚：这个模块依赖谁？它对外提供什么能力？哪些事它明确不做？最后这条最重要——不写「不做什么」的模块，边界一定会被侵蚀。
  5. 第五步：排优先级与定复杂度
    用 MoSCoW 或简单三档：必须有 / 该有 / 可以有。给每个模块标一个复杂度（简单/中等/复杂），这是排工期和分配人力的依据。

02

业务流程建模与状态机设计

解决两个问题：事情按什么顺序发生？东西在各个阶段是什么状态？

一句话业务流程＝谁在什么时候做了什么；状态机＝某个「东西」在生命周期里处于什么状态、能被什么事件推到下一个状态。

流程像一条路上的路线图，状态机像路上每个红绿灯的规则表。只有路线图没有规则表，路上堵车；只有规则表没有路线图，红绿灯装错了地方。

2.1 业务流程：先说清「谁」

画流程最容易犯的错是「一条线走到底」——因为真实的系统里，不同角色做的事是并行的。所以第一步是列角色：

买家卖家系统支付平台管理员

然后画泳道图：每条泳道一个角色，每个方框是一个动作，方框之间的箭头是流转，菱形是判断。

主流程（文字版）

  1. 卖家：发布书籍 → 上架待售
  2. 买家：搜索浏览 → 选定书籍 → 提交订单（创建订单，锁书 15 分钟）
  3. 买家：支付（订单转「已支付」）
  4. 卖家：收到通知 → 确认交接方式 → 生成交接码 → 双方交接
  5. 买家：输入交接码确认收货（订单转「已完成」）
  6. 双方：互评（更新信誉分）

别忘了异常分支

只写主流程的设计叫「理想世界设计」，上线后第一个被投诉的就是它。异常分支至少要覆盖这五类：

异常类型书接力例子需要设计的点
用户反悔下单后不付款、下单后想取消超时时长、能否取消、库存何时释放
外部依赖失败支付网关超时、回调丢失重试策略、幂等、最终一致还是强一致
并发冲突两人都想买最后一本锁的粒度、超卖防护
数据不合法交接码输错、被举报书籍校验点在哪、错误码是什么、能否申诉
权限不足学生想删别人的订单鉴权在哪一层拦、返回什么

2.2 从流程到状态机：把「对象」拎出来

流程描述的是动作序列，状态机描述的是某个对象的属性变化。做法：从流程里找出那些会经历多个阶段的东西——订单、书籍、支付单、退款单——对每一个画状态机。

判定口诀

一个东西如果「现在处于某种状态，而且这个状态会影响下一步能做什么」，它就该有状态机。状态的价值在于约束——它把「什么时候可以做什么」写死，代码里只需要判一次，UI 上只需要决定按钮显不显示。

2.3 状态机的四个要素

状态 State

对象此刻的样子。用「已支付」「待发货」这种能一眼看出时间点的名词。不要用「支付中」（到底是进行中还是等待中？）。

事件 Event

触发状态变化的动作。用「用户点击取消支付」「支付平台回调成功」这种具体的、可被观察到的描述。

守卫 Guard

转移发生的前提条件。如「退款金额 ≤ 订单实付金额」「距下单 ≤ 48 小时」。没有守卫的状态机，往往上线后被业务规则打脸。

动作 Action

转移时顺带做的事。如「释放库存锁」「写审计日志」「发通知给买家」。动作是状态机和业务流程的接口。

2.5 状态机的四个经典陷阱

① 状态爆炸

状态两两组合导致数量爆炸（订单状态 × 交接状态 = 12 个状态）。解法：拆成多个正交的独立状态机，或用子状态机。

② 漏事件

只写了「正常路径」，忘了「用户反悔」「超时」「外部失败」这些边。上线后必然要打补丁。

③ 非法转移没兜底

代码里遇到一个状态机里不存在的转移，要么崩要么静默。正确做法：显式抛错 + 定义清楚「非法转移返回什么错误码」。

④ 状态与流程步骤混淆

把「填写地址」「填写备注」当成订单状态——它们是流程步骤，不是订单的属性。判断方法：这个状态会持续存在吗？会显示在订单列表里吗？

2.6 状态机 → 代码：一个能直接用的骨架

# 状态转移表就是代码：新增状态时，加一行；改规则时，改守卫。
ORDER_TRANSITIONS = {
    ("CREATED", "pay"):            ("PAID",        "write_payment_record"),
    ("CREATED", "cancel"):         ("CANCELLED",   "release_stock_lock"),
    ("PAID",    "ship"):           ("SHIPPED",     "generate_handover_code"),
    ("PAID",    "apply_refund"):  ("REFUNDING",   "create_refund_order"),
    ("SHIPPED",  "confirm"):        ("COMPLETED",   "settle_seller_amount"),
    ("SHIPPED",  "apply_refund"):   ("REFUNDING",   "freeze_settlement"),
    ("REFUNDING", "approve"):      ("REFUNDED",    "refund_to_user"),
    ("REFUNDING", "reject"):       ("PAID",        "notify_applicant"),
    ("COMPLETED", "auto_close"):    ("CLOSED",      None),
}

def transit(order, event, **guard):
    rule = ORDER_TRANSITIONS.get((order.status, event))
    if rule is None:
        raise IllegalTransition(order.status, event)   # 兜底：显式失败
    target, action = rule
    if not check_guard(target, guard):
        raise GuardNotSatisfied(event)
    order.status = target
    if action:
        ACTIONS[action](order)
    log_transition(order, event)          # 审计日志：谁在什么时候把订单推到了哪
    notify_related_modules(order, event)  # 发领域事件，通知模块只订阅、不反向调用
    return order

03

UI/UX 原型设计：让人知道下一步该干什么

解决三个问题：有哪些页面？页面之间怎么跳？每个页面上用户要干什么？

一句话UI 原型＝把「模块」翻译成「人眼可见的界面与操作路径」，让用户在没写代码之前就能体验到你的设计。

UI 解决「长什么样」，UX 解决「好不好用」。对校园项目来说，UX 的权重往往高于 UI：一个丑但步骤清晰的页面，比一个漂亮但让人迷路的面团有用得多。

3.1 先分清 UI 与 UX

UI（User Interface）

看得见的部分：布局、配色、字号、控件样式、间距。它回答「界面由什么组成」。

UX（User Experience）

用起来的感觉：步骤多少、提示是否清楚、出错时能否自救。它回答「用户能否顺利达成目标」。

自测法

把你的原型给一个没参与设计的人看，只说一句话：「这是一个校园二手书网站，帮我买一本《数据结构》。」如果他需要你指导，就说明 UX 有问题，这跟界面好不好看无关。

3.2 三步法：信息架构 → 页面 → 交互

  1. 第一步：列页面清单（信息架构）
    把第 1 章的每个功能模块映射到它需要的页面。一个模块通常对应 1–3 个页面（列表 / 详情 / 编辑）。同时画出导航结构（谁是一级、谁是二级、怎么返回）。
  2. 第二步：定关键页面的结构
    先做 5–8 个最关键的页面线框，别的先别管。关键 = 使用频次最高 或 流程中最容易出错。
  3. 第三步：串交互流程
    把页面用箭头连起来，标出每一步「用户点了什么」「系统返回什么」「失败了怎么回来」。这一步最容易被跳过，也最容易出事。

3.4 原型的三种保真度

低保真：纸面 / 灰盒

用纸笔画方框，或用纯 HTML 摆几个灰底方块。成本 30 分钟。用途：验证流程与信息是否够用——把方块拿给同学看，问「你知道自己现在在哪、下一步要点哪里吗」。

中保真：线框图

用 Figma 组件库摆好布局、填上真实文字（中文占位符效果远好于 Lorem ipsum）。用途：验证信息层级与文案。

高保真：可点击原型

加上颜色、字体、动效，做成能点的链接。用途：验证动线与状态切换（尤其是订单状态变化后按钮怎么变）。

别一上来就做高保真

在流程还没想清楚时画漂亮界面，是在给错误方案化妆。先低保真跑通，再逐步升保真度。

3.7 可访问性（a11y）最低要求

  • 正文与背景对比度 ≥ 4.5:1（用在线对比度工具一测便知，很多学生项目连 3:1 都不到）。
  • 不要只用颜色区分状态——加上文字或图标（色弱用户看不出「已支付」的橙色和「待支付」的黄色）。
  • 表单控件必须有可见的 label，不能只有 placeholder（placeholder 一输入就消失，且屏幕阅读器不友好）。
  • 键盘可达：Tab 顺序合理，弹窗能 Esc 关闭，焦点可见。
  • 移动端：先设计手机版（校园场景多为手机使用），再考虑桌面版。

04

系统架构设计与技术选型

解决两个问题：系统的骨架长什么样？为什么用这套技术而不是那套？

一句话架构设计＝在「质量目标」约束下，对系统的结构、边界、通信方式、技术栈做出有依据的取舍。

架构不是画一堆方框加箭头，而是做决策。每一个方框都该对应一句「我们为什么这么切」，每一条线都该对应一句「为什么它们要通信」。答不上来的，说明还没想清楚。

4.1 先定质量目标（不然后面全是空谈）

架构好不好，只能对照目标来评判。开始设计前，先把非功能需求量化。

质量属性学生版常见写法（不合格）合格写法（可验证）怎么验证
性能「要快」「书籍列表接口 P95 响应 < 300ms」压测脚本
并发「支持多人使用」「峰值 200 并发下错误率 < 0.1%」压测
可用性「不能挂」「核心下单链路可用性 99.9%」监控告警
一致性「数据要准」「下单与库存锁定强一致；消息通知最终一致（≤5s）」并发测试 + 延迟监控
可维护「代码要好维护」「新同学 1 天内能独立提交订单模块改动」上手实测
成本「要省钱」「月成本 ≤ 50 元，用免费层」账单
安全「要安全」「密码用 bcrypt 存储；所有订单接口校验归属」安全测试用例

4.2 四步架构法

  1. 第一步：把质量目标变成约束
    从上表挑出 3–5 条最关键的，写在架构文档最前面。比如书接力：并发 200、成本 ≤50 元、3 人 3 个月。
  2. 第二步：拆「计算流」和「数据流」
    计算流＝请求怎么走；数据流＝数据怎么进来、怎么落库、怎么出去。先画这两张图，比直接选框架靠谱得多。
  3. 第三步：选架构风格
    单体？模块化单体？微服务？事件驱动？先选风格，再选技术。
  4. 第四步：选技术栈并写决策记录
    每个关键选择写一条 ADR（Architecture Decision Record）：背景、选项、决定、后果。三个月后你不会记得为什么用 A 不用 B，ADR 会记得。

风格长什么样适合代价
分层单体表现层 → 应用层 → 领域层 → 基础设施层，同一个部署单元绝大多数学生项目、绝大多数中小系统规模大了以后扩展受限
模块化单体单体，但内部按业务模块划包，模块间只走公开接口想为将来拆微服务留门，但当下不想付运维代价需要严格纪律（模块不能互相偷看内部）
微服务订单、书籍、支付各自独立部署，服务间走网络调用团队 ≥ 10 人、某模块需独立扩容、有强合规隔离要求分布式带来的复杂度：网络故障、分布式事务、观测成本陡增
事件驱动各模块只发事件，谁关心谁订阅（如消息通知）需要「一个动作触发多个下游」的场景链路追踪困难，调试成本高
Serverless函数 + 托管数据库，按量计费流量波动大、有现成 BaaS 可用冷启动、厂商锁定、长任务不友好
给 3 人团队的最重要一条建议

不要上微服务。不是因为「简单」，而是因为微服务要付出的是分布式系统税：服务间调用会失败要重试、数据会不一致要补偿、日志散在各处要聚合链路、部署从 1 个变成 8 个。这笔税要用「团队规模」来还——业界经验值是每微服务至少配 0.5–1 个运维/后端。3 个人的团队上 6 个微服务，等于 3 个人当 6 个运维。

正确做法：模块化单体 + 清晰的模块边界 + 事件解耦。等你真的遇到「订单模块需要单独扩容」时，再把它拆出去——那时你有了真实数据支撑决策，而不是为了简历好看。

4.4 分层：每层干什么，依赖往哪边倒

层职责能不能依赖别的层书接力举例
表现层 / 接口层接收请求、校验入参格式、组装响应、HTTP 状态码只依赖应用层POST /orders 控制器
应用层编排用例：开启事务、调用多个领域能力、发事件依赖领域层「创建订单」用例：校验书 → 锁库存 → 建单 → 发事件
领域层业务规则与状态机，不依赖任何框架和数据库不依赖其它层（最干净的一层）订单状态机、金额计算规则、退款守卫条件
基础设施层数据库访问、缓存、第三方 SDK、文件存储实现应用/领域层定义的接口MySQL 仓储、Redis 缓存实现、支付网关客户端
依赖倒置：让领域层不认识 Spring

「领域层不依赖框架」听起来抽象，其实有很实际的好处：你的状态机代码可以不启动数据库、不启动 Spring 就跑单元测试，跑得飞快；将来换框架，这块代码一行不用改。这在考试和面试里都属于加分项。

05

数据库三层建模与 ER 设计

解决三个问题：业务上有哪些「东西」？它们之间是什么关系？最终怎么落到具体的表和字段？

一句话数据库建模＝把业务世界翻译成结构化数据。分三层做，每层解决不同的问题。

很多同学一上来就建表，结果字段重复、关系混乱、后期无法扩展。三层建模的价值就在于：概念层保证你想清楚了，逻辑层保证结构不重复，物理层保证能跑得快。

5.1 概念层：先问「业务世界里有什么东西」

概念层完全不谈数据库。它的产出是实体、属性、关系和业务规则，可以直接拿给产品经理和测试同学看，他们不需要懂数据库也能读懂。

找实体：名词就是候选

回到第 2 章的流程和状态机：里面出现的反复出现的名词就是实体候选。书接力里：用户、书籍、订单、订单项、支付单、退款单、评价、消息、分类、交接记录。

别把「动作」当实体

「下单」是动作，不是实体，它属于订单。「收藏」是动作，它应该作为用户和书籍的一个关系存在，而不是一个叫「收藏表」的表。

定关系：三种基数

关系含义例子建模提示
1 : 1一对一一个用户 ↔ 一份学生证把 1 端的主键作为外键放到 N 端，通常不单独建表
1 : N一对多一个用户 ↔ 多个订单N 端存 1 端的主键作为外键
M : N多对多多个订单 ↔ 多本书籍必须拆成关联表，关联表通常带自己的业务属性

书接力的「订单 ↔ 书籍」就是 M:N，必须拆出订单项表。而订单项不是纯关联表——它有「成交价」「成色」等属性，这些是下单那一刻的快照，这一点极其重要（见 5.4）。

5.2 逻辑层：规范化与主键设计

什么是规范化（用大白话）

范式人话解释反例
1NF每个字段只放一个值，不能塞数组或逗号串tags = "高数,线代,概率" 放一个字段里
2NF非主键字段不能「部分依赖」复合主键订单明细表主键是(订单号,行号)，却把订单总价也存进去
3NF非主键字段不能传递依赖主键（即不能有「间接依赖」）订单表里存 买家所在学校——学校只依赖用户，与订单无关

规范化的本质是消除重复。重复不只是浪费空间，更重要的是更新不一致：同一个信息存了两份，改了一处忘了另一处，数据就自相矛盾了——这是线上事故的高频来源。

但快照字段是故意的「反范式」

订单项里存「成交价 18 元」，即便书籍当前价格改成 20 元，这条订单项仍然记 18 元。这不是设计错误，是刻意为之——因为订单要反映「当时发生了什么」。这种字段叫「快照字段」，是业务规则决定的，不是偷懒。要在文档里明确写出来：哪些字段是快照、快照时点是什么时候。

主键怎么选

自增 ID（bigint）

优点：简单、索引小、写入快。缺点：可猜测（能看出总订单数）、跨库合并麻烦、分布式要协调。适合：内部主键。

UUID / ULID

优点：全局唯一、可离线生成、不泄露业务量。缺点：占空间、随机写入影响索引。适合：需要对外暴露或分库场景；用 ULID（带时间前缀）能兼顾。

业务主键

如订单号「BR20240513001」。优点：可读、可对账、可作为幂等键。适合：对外暴露的编号；注意它不能替代内部主键（规则一旦变就麻烦）。

通用建议

内部用 bigint 自增做主键，对外用独立的业务编号做唯一索引。两者分离，是很多生产系统的标准做法。

5.3 画 ER 图

ER 图（Entity-Relationship Diagram）就是「实体关系的地图」。画法约定：

  • 实体＝矩形（表名 + 关键属性），
  • 关系＝线上标注关系名 + 两端标基数（1、N、M），
  • 属性＝列出来，主键加下划线或标 PK，外键标 FK。

5.4 物理层：字段、索引与约束

逻辑层说「有一张订单表」，物理层要回答：字段用什么类型？多长？要不要默认值？索引建在哪？

决策点原则例子
金额用整数分或 decimal，绝不用 float/doubletotal_amount DECIMAL(10,2)
字符串定长且短的用 CHAR，其余用 VARCHAR 并显式给长度VARCHAR(64)
时间统一用 UTC 存储，展示时转本地时区created_at DATETIME
状态/类型用 ENUM 或 CHAR+检查约束，别用魔法数字status ENUM('CREATED','PAID',...)
软删除需要保留历史用 deleted_at；否则物理删除更简单deleted_at DATETIME NULL
审计字段每张业务表都要有 created_at / updated_at—
外键能用就用，能挡住脏数据；不用时要自己保证一致FOREIGN KEY (book_id) REFERENCES book(id)
唯一约束业务唯一性一定要落库，不能只靠代码判断UNIQUE(order_id, reviewer_id)

建表脚本示例

CREATE TABLE orders (
  id            BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  order_no     VARCHAR(32)     NOT NULL COMMENT '业务订单号，对外暴露',
  buyer_id     BIGINT UNSIGNED NOT NULL COMMENT '下单人',
  status       ENUM('CREATED','PAID','SHIPPED','COMPLETED','CANCELLED','REFUNDING','REFUNDED','CLOSED') NOT NULL DEFAULT 'CREATED',
  total_amount DECIMAL(10,2)   NOT NULL DEFAULT 0.00,
  handover_method VARCHAR(32)  NULL COMMENT '交接方式枚举',
  expires_at    DATETIME       NOT NULL COMMENT '待支付过期时间 = created_at + 30min',
  created_at    DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME       NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at    DATETIME       NULL,
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_buyer_status (buyer_id, status, created_at),  -- 我的订单列表
  KEY idx_status_expire (status, expires_at),           -- 超时取消扫描任务
  CONSTRAINT fk_orders_buyer FOREIGN KEY (buyer_id) REFERENCES users(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci;
索引的直觉

索引像一本书的目录，代价是写入变慢、占空间。两条经验：
① 最左前缀——索引 (buyer_id, status, created_at) 能高效支持「按 buyer_id 查」「按 buyer_id+status 查」「按 buyer_id+status 按时间排序」，但单独按 status 查用不上它。
② 为查询建索引，而不是为字段建索引。先写出真实的查询语句，再决定索引；建完用 EXPLAIN 看有没有真的走索引。

06

API 设计与数据契约

解决三个问题：模块之间怎么说话？说话时用哪种格式？格式变了老代码怎么办？

一句话API 设计＝给系统开对外「窗口」，规定每个窗口要什么、给什么、什么时候不给、错了怎么表达。数据契约＝把「窗口的形状」写成机器可读的正式文件。

可以类比成快递：API 是「寄件流程」（下单 → 揽收 → 运输 → 派送），数据契约是「面单格式」。面单格式改了一版，寄件人按新格式填，物流系统按新格式读——但如果只有一个人改了，就全乱了。契约的作用就是让改动是「协商出来的」，而不是「通知一下就完事」。

6.1 先理解「契约」这两个字

一份 API 文档不只是一张接口清单，它是一份承诺。承诺的内容包括：

形状（Shape）

请求体有哪些字段、类型是什么、哪些必填；响应体长什么样；错误响应长什么样。

语义（Semantics）

这个接口是干什么的；同一个状态码在不同接口含义是否一致；幂等吗；要不要鉴权；分页怎么翻。

兼容性（Compatibility）

以后新增字段行不行？删除字段行不行？改字段类型行不行？这些必须提前说清楚，否则合作方会炸。

版本与生命周期（Versioning）

什么时候废弃、怎么通知、多久过渡期。不写这一条，接口会永远改不动。

AI 时代这条更值钱

以前「写完代码再补接口文档」还能凑合；现在 AI 大量生成调用代码，如果契约本身是模糊的，AI 会替你猜出一个形状，猜错了还不告诉你。所以契约必须是机器可读的唯一事实源——OpenAPI 文件要进代码仓库，代码要由它生成或校验，而不是各写各的。

6.2 REST 风格的基本约定

方法语义是否幂等典型路径
GET读取资源是GET /books/{id}
POST创建资源 / 执行动作否（需幂等键）POST /orders
PUT整体替换是PUT /books/{id}
PATCH局部更新否（视语义）PATCH /books/{id}
DELETE删除资源是DELETE /books/{id}
  • URL 用名词，不用动词：/orders 好过 /createOrder。动词应该放在 HTTP 方法里。
  • 状态码用对：200 成功 / 201 已创建 / 400 参数格式错 / 401 未登录 / 403 无权限 / 404 不存在 / 409 状态冲突（如订单已支付不能再取消）/ 422 语义校验失败 / 500 服务端错误。
  • 过滤、排序、分页用查询参数：GET /books?category=12&keyword=数据结构&sort=price_asc&page=1&page_size=20
409 是个被低估的状态码

很多学生项目把所有失败都写成 400 或 200 + 错误 message。但「订单状态冲突」和「参数格式错」是两类完全不同的错误，前端处理方式也不同：前者要刷新页面重新引导，后者要就地提示重填。用对状态码，前端才写得出正确的交互。

6.3 统一错误结构

{
  "code": "ORDER_STATE_CONFLICT",          // 机器可读：前端据此分支
  "message": "订单已支付，无法取消",          // 人可读：直接展示
  "details": [
    { "field": "orderId", "reason": "current_status=PAID" }
  ],
  "trace_id": "a1b2c3d4"                // 排障用：一键定位日志
}

好处：前端能用 code 做逻辑分支（比如 ORDER_STATE_CONFLICT → 刷新订单页并提示），能用 message 直接展示，运维能用 trace_id 查日志。三方各取所需，不用在错误 message 里做字符串匹配。

6.4 幂等性：POST 重复提交怎么办

用户网络卡了，连点两次「提交订单」——如果没有幂等设计，你会创建两个订单、扣两次钱。这是真实事故。

做法：客户端生成一个 Idempotency-Key（UUID），放在请求头里；服务端记住「这个 key 处理过，结果是什么」，重复请求直接返回上次的结果，不再执行。

# 伪代码：幂等键的实现
key = request.headers["Idempotency-Key"]
if key in redis:                       # 24h 内有效
    return redis.get(key)                  # 直接返回上次结果
result = create_order(request.body)
redis.set(key, result, ex=86400)
return result

注意：订单号本身也可以天然当幂等键——用「买家 ID + 业务唯一标识」生成订单号，重复请求天然撞号。这是更稳妥的做法，因为不依赖客户端配合。

6.5 OpenAPI：让契约变成机器可读的文件

OpenAPI（Swagger 规范）用 YAML/JSON 描述整套 API：有哪些路径、每个路径有哪些操作、请求体长什么样、响应有哪些状态码、每个字段什么类型。

openapi: 3.1.0
info:
  title: 书接力 API
  version: 1.0.0
  description: 校园二手教材流转平台
servers:
  - url: https://api.bookrelay.edu.cn/v1
paths:
  /orders:
    post:
      summary: 创建订单
      operationId: createOrder
      parameters:
        - name: Idempotency-Key
          in: header
          required: true
          schema: { type: string, format: uuid }
          description: 幂等键，24 小时内相同 key 只创建一次
      requestBody:
        required: true
        content:
          application/json:
            schema: { $ref: '#/components/schemas/CreateOrderRequest' }
      responses:
        '201':
          description: 创建成功
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Order' }
        '409':
          description: 书籍已被锁定或订单状态冲突
          content:
            application/json:
              schema: { $ref: '#/components/schemas/ErrorResponse' }
        '401': { description: 未登录或登录已失效 }
components:
  schemas:
    CreateOrderRequest:
      type: object
      required: [bookId, handoverMethod]
      properties:
        bookId:
          type: integer
          format: int64
        handoverMethod:
          type: string
          enum: [LIBRARY_WEST, DORM_LOBBY, COURIER]
        remark:
          type: string
          maxLength: 200
    Order:
      type: object
      required: [orderNo, status, totalAmount, items]
      properties:
        orderNo:      { type: string }
        status:       { type: string, enum: [CREATED, PAID, SHIPPED, COMPLETED, CANCELLED, REFUNDING, REFUNDED, CLOSED] }
        totalAmount:  { type: number, format: double }
        expiresAt:    { type: string, format: date-time }
        items:
          type: array
          items: { $ref: '#/components/schemas/OrderItem' }
    OrderItem:
      type: object
      properties:
        bookId:   { type: integer, format: int64 }
        title:    { type: string }
        unitPrice: { type: number }
    ErrorResponse:
      type: object
      required: [code, message]
      properties:
        code:    { type: string }
        message: { type: string }
        traceId: { type: string }

注意订单状态机的枚举值，出现在 OpenAPI 的 Order.status 里。

这不是巧合——状态机的状态集合就是 API 的契约一部分。前端拿到 status=PAID 就显示「申请退款」按钮，靠的是两边共用同一份枚举定义。第 7 章的一致性核对中，这一条会被专门检查。

6.6 兼容性规则（团队协作的底线）

改动兼容性说明
新增可选字段✅ 安全但老客户端要能容忍未知字段（多数语言默认忽略）
新增枚举值⚠️ 有风险老客户端遇到未知值可能崩——前端要用兜底分支
新增接口✅ 安全—
删除字段 / 改字段名❌ 破坏性必须等所有调用方迁移完，且要保留一个版本周期
改字段类型❌ 破坏性哪怕 int → int64 也可能溢出
改字段语义（名字不变含义变）❌ 最危险编译通过、测试通过、数据全错——所以字段名要能表达语义
新增必填字段❌ 破坏性老客户端没传 → 直接 400

版本化策略三选一：

  • URL 版本：/v1/orders、/v2/orders。直观、易灰度，但 URL 里多个 v 略丑。
  • Header 版本：Accept: application/vnd.bookrelay.v2+json。URL 干净，但调试和文档门槛高。
  • 字段版本：响应里带 version 字段，同一接口同时返回新旧字段。适合加字段类演进。

学生项目推荐URL 版本：简单、网关能按路径路由、文档好写。

6.7 契约怎么被真正执行

契约即代码

OpenAPI 文件进仓库；前端类型、后端 DTO、Mock 数据都从它生成。改契约 → 重新生成 → 编译不过就说明有人没跟上。

Mock 先行

后端还没写完，前端用 Mock Server 按 OpenAPI 造数据。前后端可以真正并行，不用等接口。

契约测试

CI 里跑「响应是否符合 OpenAPI 描述」的测试，防止实现悄悄跑偏。

消费者驱动契约

下游（前端）声明「我需要哪些字段」，上游 CI 里验证自己是否满足（Pact 等工具）。

AI 在 API 设计阶段的用法

用法一（生成契约草稿）：把功能模块表 + 状态机给 AI：「为订单模块设计 REST 接口清单，包含路径、方法、请求字段、响应字段、错误码、幂等要求、鉴权要求。」它能帮你穷举接口，然后你删改。

用法二（把契约翻译成代码）：FastAPI 里直接写类型注解，框架自动生成 OpenAPI；或者用 datamodel-code-generator 从 OpenAPI 生成 TS 类型 / Java DTO / Mock 数据。这条链路是 AI 时代最高杠杆的用法——契约是唯一事实源，其余全部自动派生。

用法三（审接口设计）：「请扮演 API 设计评审，逐个接口检查：资源命名是否规范、状态码是否用对、是否缺分页、是否缺错误码、是否有幂等风险、是否泄露敏感字段、字段命名是否一致。」

用法四（写 SDK / 联调代码）：契约定稿后，让 AI 根据 OpenAPI 生成调用示例、前端 API 封装、Mock 数据、契约测试用例。

风险提示：AI 生成的接口常常「看起来很全」但缺业务约束（比如不知道「订单 30 分钟未支付自动取消」这件事）。约束只能来自你的设计文档——这正是前五章存在的意义。

动手任务 6-A：为书接力写一份真实的 OpenAPI（60 分钟）
  1. 选 6 个接口：创建订单、查询订单列表、查询订单详情、取消订单、申请退款、发布书籍。
  2. 为每个接口写：路径、方法、鉴权、请求字段（含校验规则）、成功响应、至少 2 个错误响应。
  3. 用 components/schemas 复用公共结构（订单、错误、分页）。
  4. 统一错误码表：至少列 10 个错误码，写清触发条件和前端应对方式。
  5. 标出哪些接口需要幂等键，哪些是幂等的。
  6. 把文件放进 docs/api/openapi.yaml，并用它生成一份 Mock 数据。

自检：把这份 OpenAPI 交给一个没参与设计的同学，让他说出「订单从下单到完成会经历哪些接口调用」。如果他数出来的接口数和你设计的流程对不上，说明漏了。

07

跨设计产物一致性核对与设计评审

解决一个问题：八份设计产物之间，有没有互相打架的地方？

一句话一致性核对＝把八份产物放在一起做交叉比对；设计评审＝用一双专业的眼睛和一套流程，把比对结果变成有结论、有责任人、有期限的行动项。

这是整个方法论里投入产出比最高的一步。它不需要任何新工具，只需要一张表格和一次认真的会。但绝大多数团队跳过它，然后在上线前一周疯狂返工。

7.1 一致性问题的真实样貌

这些不是编出来的段子，而是设计阶段最高频的漏检项：

#症状后果发现阶段
1功能模块里有「退款申请」，但 API 清单里没有退款接口前端做不了，开发互相甩锅联调期
2状态机有「退款中」状态，但原型里没有这一页的界面用户到了这个状态不知道该干嘛测试期
3ER 图里有 books.isbn 字段，API 响应里没有列表页要显示 ISBN，白屏联调期
4架构图里只有 MySQL，没画 Redis，但代码里用了缓存新同学部署时忘了装 Redis部署期
5订单状态机的「已关闭」状态，数据库 ENUM 里没有定时任务一跑就报数据截断上线后
6原型上有「举报」按钮，但没有举报相关的模块和表点了没反应，或数据无处存测试期
7错误码在三个模块里各写了一套，含义冲突前端按错误码分支全乱联调期
8第 4 章说并发 200，但第 5 章的库存方案是「先查再写」，没有锁超卖压测期

注意第 5、8 条：它们不是「文档写漏了」，而是设计本身有洞。这说明一致性核对的价值不止于「查漏」，还要能发现设计层面的矛盾。

7.2 一致性核对矩阵（可直接打印使用）

把八份产物两两交叉，总共就是下面 10 类核对项。每一行都要有结论：一致 / 不一致（写清楚谁改）/ 不适用（写清理由）。

#核对项怎么查（操作方法）不一致的表现
C1需求 → 功能模块把需求里的功能点逐条打勾，找出无人认领的需求里的功能没落到任何模块
C2功能模块 → 业务流程每个模块的核心功能点是否都在流程里有对应动作模块有功能但流程走不到
C3业务流程 → 状态机流程中每个「对象的阶段」是否都在状态机里订单有阶段但状态机没这个状态
C4状态机 → UI 原型每个状态是否有对应页面；每个出口事件是否有对应按钮状态存在但界面无入口
C5功能模块 → API模块的每个对外能力是否有对应接口模块说要提供能力但没接口
C6API ↔ 数据模型逐接口比对：请求字段、响应字段 ↔ 表字段（读写双向）接口要返回的字段表里没有
C7数据模型 → 架构每张表/每个缓存是否在架构图里有对应的存储用了缓存但架构没画
C8原型 → API每个页面上显示的每个字段，是否都有接口能提供页面要显示 ISBN，接口没返回
C9状态机 ↔ 数据模型状态机里的每个状态值是否在表字段的枚举里枚举缺值，定时任务报错
C10全局一致性错误码表、权限规则、命名规范在所有产物中是否一致同一错误码两个含义

怎么把核对做实（三个技巧）

  1. 用机器做能机器做的。写个小脚本，从 OpenAPI 里抽出所有字段名，和 DDL 里的列名做集合差集——差集里出现的名字就是待查项。三十秒的事，别靠肉眼。
  2. 用「反向」查一遍。正向查「每个功能都有接口了吗」，反向查「每个接口都对应哪个功能需求」。正反向结果不一致的地方，通常是设计冗余或遗漏。
  3. 拉一个不熟悉项目的人来问。「这个设计要怎么实现退款？」让对方口头描述一遍流程。他卡住的地方，就是设计没讲清楚的地方。这招叫「新人走查」，对 UI 和 API 尤其有效。
# 一致性核对辅助脚本（示意）：比对 API 响应字段与数据库列名
import yaml, re

api = yaml.safe_load(open("docs/api/openapi.yaml", encoding="utf-8"))
ddl = open("docs/db/schema.sql", encoding="utf-8").read()

# 粗略抽取 DDL 中的列名
columns = set(re.findall(r"^\s{2,4}(\w+)\s+(?:BIGINT|VARCHAR|CHAR|INT|DECIMAL|DATETIME|ENUM|TEXT)",
                          ddl, re.MULTILINE))

# 抽取所有响应 schema 的属性名
props = set()
for name, schema in api["components"]["schemas"].items():
    props |= set(schema.get("properties", {}).keys())

missing = sorted(props - columns)
if missing:
    print("[C6] API 响应里出现但数据库没有的字段：")
    for m in missing:
        print("  -", m)
else:
    print("[C6] OK：响应字段均可在数据模型中找到对应列")

7.3 设计评审：把核对结果变成决策

一致性核对是「你自己查」，设计评审是「大家一起查」。评审的价值在于：不同角色看同一个东西，关注点不同。前端看交互，后端看边界，测试看可测性，架构师看耦合。

评审会的正确流程（90 分钟）

  1. 会前：材料先行（提前 2 天发出）
    设计文档、评审范围说明、本次要评审的开放问题列表、一致性核对矩阵结果。评审不是让所有人从头读文档，而是让作者先说清「我有 3 个拿不准的点，请大家帮我定」。
  2. 会中：作者讲解 + 提问 + 记录
    限时 20 分钟讲设计，40 分钟提问，10 分钟整理结论。指定一名记录人，只记「问题 + 结论 + 责任人 + 期限」，不记闲话。
  3. 会中：按检查表逐项过
    用固定的检查表（见 7.4）逐项过，避免「大家都觉得挺好的」然后散会。
  4. 会后：输出评审纪要与行动项
    纪要 = 结论 + 问题清单 + 行动项 + 遗留决策。行动项必须有责任人和截止时间，否则等于没记。
  5. 会后：问题闭环
    每个行动项完成后标记关闭；重新设计受影响的产物；必要时重新评审（只针对变更部分）。

缺陷分级：避免「所有问题都是致命问题」

级别定义处理
Blocker设计存在逻辑矛盾或无法实现，不改就做不下去必须改，评审不通过
Major会显著增加开发量或引入高风险，但有绕行方案本次评审必须给出方案
Minor命名、表述、细节不一致记录，择机修
Suggestion优化建议，不影响正确性作者自行决定

7.5 实战：找出案例里埋的三个问题

下面这份「设计片段」来自一个真实的课程项目。它看起来很完整，但有三个不一致。试试找出来。

设计片段

功能模块表（摘录）：① 用户与账号　② 书籍管理　③ 订单管理　④ 支付　⑤ 消息通知　⑥ 数据统计

状态机（摘录）：订单 = 待支付 → 已支付 → 待交接 → 已完成 / 已取消。（无退款相关状态）

数据库 DDL（摘录）：orders.status ENUM('CREATED','PAID','SHIPPED','COMPLETED','CANCELLED')；表中无 refund 相关表。

OpenAPI（摘录）：POST /orders、GET /orders、GET /orders/{id}、POST /orders/{id}/cancel、POST /payments。（无退款接口）

原型：订单详情页有「申请退款」按钮。

架构图：应用层有「订单用例 / 书籍用例 / 支付用例 / 通知用例 / 统计用例」。

点击查看答案（三个不一致）
  1. C5/C6 不一致（跨模块）：功能模块表和架构图里有「数据统计」，但 API 清单里没有任何统计接口，也没有对应的表设计。
    → 影响：前端做不了数据看板；开发要现设计。
    → 动作：要么补接口与表，要么把「数据统计」从本期范围移出并标注为「后续迭代」。
  2. C4 不一致（状态 ↔ UI）：原型上有「申请退款」按钮，但状态机没有「退款中」状态，数据库 ENUM 也没有对应值，API 没有退款接口。
    → 影响：按钮点了没接口；真要走退款流程，状态无处落。
    → 动作：要么补齐「退款中 → 已退款/已驳回」的状态、枚举、接口、表；要么本期不做退款（同时把按钮去掉）。三处必须一起改，只改一处就是新的不一致。
  3. C1 不一致（需求 ↔ 模块）：模块表列了「消息通知」，但 API 清单中没有任何通知查询接口，原型也没有消息中心页面。
    → 影响：用户在订单状态变化后收不到提示，或没有地方查看历史通知。
    → 动作：补 GET /notifications + 消息表 + 消息中心页面；或明确「本期只用系统推送，不做站内信」。

规律：第 2 条是最典型的——一个业务决策（要不要支持退款）横跨了 4 份产物，任何一处漏改都会产生不一致。所以核对不是逐份文档看，而是沿着一条业务线索横切所有产物。

用 AI 做一致性核对：它擅长穷举，但不擅长判断

正确用法：把多份产物（模块表、状态机、DDL、OpenAPI、原型说明）一起喂给 AI，让它按你给的 C1–C10 清单逐项比对，输出「可能的不一致点」列表，然后你去核实。

下面是我的 5 份设计产物：功能模块表、订单状态机、数据库 DDL、OpenAPI、原型页面说明。
请按以下 10 类核对项做交叉比对，找出可能的不一致：
C1 需求↔模块　C2 模块↔流程　C3 流程↔状态机　C4 状态机↔UI　C5 模块↔API
C6 API↔数据模型　C7 数据模型↔架构　C8 原型↔API　C9 状态机↔枚举　C10 全局规范

输出格式：核对项编号 | 涉及的两份产物 | 描述 | 建议动作 | 严重度
要求：
- 只输出你能在给出的材料中找到文本依据的不一致，不要脑补
- 不确定的标为「待人工确认」
- 不要修改我的任何产物
【粘贴 5 份产物】

价值所在：人类做这类交叉比对最容易疲劳和漏项——第 8 份文件就开始走神了。AI 不会。但AI 会误报（它可能没看懂你的隐含约定），也会漏报（它读不到你脑子里的业务规则）。所以流程是：AI 扫，人核。

更狠的用法：让 AI 扮演「三个月后接手的同事」，只给你看这些产物，问它：「如果让你来实现退款功能，你会卡在哪里？」它卡住的地方，通常就是设计没写清楚的地方。

动手任务 7-A：给自己做一次真实的一致性核对（45 分钟）
  1. 把你已有的设计产物（哪怕只是模块表 + 状态机 + 几条接口）列成清单。
  2. 打印或抄下 C1–C10 核对矩阵。
  3. 逐项过，每项必须写结论：一致 / 不一致 / 不适用（写理由）。
  4. 对每条「不一致」，写清楚：改哪份产物、改成什么、由谁改、什么时候改。
  5. 按严重度排序，先处理 Blocker。

目标：至少找出 5 个不一致点。你会发现，几乎每个项目第一次做这件事都能找出 5 个以上。

08

整合：技术设计文档（TDD）

把前面七份产物，装进一份别人能读懂、你能被追责的文档里。

一句话技术设计文档＝把八项设计产出整合成一份自洽、可评审、可施工、可追溯的单一文件（Single Source of Truth）。

整合不是「把图复制粘贴进去」。整合是做三件事：补齐断点（各章之间衔接不上的地方）、消解矛盾（不同章节说法打架）、给出结论（每一节都要有一句「所以我们决定这样」）。

8.1 TDD 与其它文档的区别

文档回答什么读者生命周期
需求文档 / PRD要做什么，为谁做业务方、产品、开发需求评审后基本冻结
技术设计文档怎么造，为什么这么造开发、测试、架构师、未来的你设计评审后冻结，改动走变更流程
详细设计这段代码怎么写具体开发者随代码演进
接口文档调用方怎么用调用方随契约演进（但 TDD 里必须有引用）

8.2 技术设计文档目录模板

可直接套用

1. 文档信息　版本号 / 状态（草稿·评审中·已批准）/ 作者 / 评审人 / 最后更新日期
2. 概述　　系统要解决什么问题（一段话）、范围边界（本期做什么、不做什么）
3. 背景与约束　业务背景、用户规模、团队与工期、技术与预算约束 ← 所有后续决策的根
4. 质量目标　　量化的非功能需求（性能/并发/可用性/一致性/成本）
5. 功能模块设计　模块清单 + 职责 + 依赖图 + 优先级
6. 业务流程与状态机　主流程、异常分支、订单/书籍状态机、状态转移表
7. UI/UX 设计　信息架构、关键页面线框、交互流程、设计规范要点
8. 系统架构　　架构图、分层职责、模块依赖、关键时序图
9. 技术选型　　选型表 + ADR 摘要（决策与后果）
10. 数据模型　概念模型、ER 图、逻辑模式、物理 DDL、索引与迁移策略
11. API 与数据契约　接口清单、OpenAPI 引用、错误码表、幂等与版本策略
12. 一致性核对与评审结论　核对矩阵结果、未决问题清单
13. 测试与验收　从业务规则推导出的验收用例要点
14. 风险与待定项　已知风险、开放问题、下一步计划
第 3 节「背景与约束」是整份文档最重要的三页

所有架构决策、技术选型、砍需求的讨论，最终都要回到这一节来判对错。没有约束的设计文档等于没有设计文档——因为任何方案都可以被辩护成「合理」。写了「3 人团队 / 3 个月 / 零预算」，那么「要不要上微服务」这个问题就有了唯一答案。

8.3 写作原则

✓ 结论先行

每章开头一句话给结论，然后才是论证。读者可能只读每章第一句，你得保证那一句就够用。

✓ 图 > 表 > 文字

一张结构清楚的图胜过三段描述。但每张图后面必须跟一句话结论——图本身不表达观点，读者会各看各的。

✓ 标注待定项

把「还没想清楚」显式标出来（【待定】），而不是含混过去。假装的确定性比诚实的未知更危险。

✓ 可追溯

每个设计决策标注它来自哪条需求/哪个约束（用 [REQ-03] 这类编号）。这在需求变更时价值巨大。

✗ 写成散文

大段文字描述系统，读者读三页也抓不住主干。

✗ 复制粘贴

把 OpenAPI 全文粘进文档而不是引用文件。文档立刻变成没人维护的坟场。

8.4 摘要段落示例（开篇要能独立成立）

2. 概述

问题：校园内二手教材流转依赖微信群与闲鱼，教材信息不透明、交易无保障、找不到书是主要痛点。

方案：构建单校范围的二手教材流转平台「书接力」，提供可检索的书籍目录、订单与状态跟踪、线下面交交接码、双方互评与信誉分。

范围：本期覆盖书籍发布与检索、下单支付、线下面交、评价、站内通知、后台审核。不包含：跨校交易、快递物流对接、教材预售与团购、支付分账给多个卖家。

关键约束：3 人团队、3 个月工期、月成本 ≤ 50 元、单校峰值 200 并发。

核心技术决策：采用模块化单体架构（Python FastAPI + MySQL + Redis），按 8 个业务模块划分内部边界，以领域事件解耦跨模块通知；库存通过 Redis 分布式锁 + 数据库行锁双重保护防止超卖。

8.6 文档的维护

  • 版本号 + 变更记录：每次改设计记一行（日期 / 改了什么 / 为什么 / 谁改的）。没有变更记录的文档，你无法判断手里这份是不是最新的。
  • 状态标记：草稿 / 评审中 / 已批准 / 已废弃。评审通过后冻结；后续改动走变更流程，不能悄悄改。
  • 与代码同仓：文档和代码放同一个仓库，一起提交、一起 review。文档在别处就一定会腐烂。
  • 定期体检：每两周花 30 分钟核对文档与代码是否还一致——这正是第 7 章那套核对矩阵的日常版本。

AI 在文档整合阶段的用法

用法一（搭骨架）：把上面 14 节模板给它，让它逐节生成「本章要写什么、需要哪些输入材料」的提纲，你往里填内容。

用法二（做「读者测试」）：「请扮演一位刚加入项目、只读这份 TDD 的开发同事，回答：① 新增一个「预约功能」需要改哪几处？② 订单超时未支付是谁负责取消？③ 前端要显示卖家昵称，字段从哪来？④ 想加一个优惠券字段，要动哪些地方？以你查到的文档内容为准，答不出就说你查不到。」它答不出的地方，就是文档写得不够的地方。这个方法比人工通读高效得多。

用法三（反向生成）：让 AI 从代码反向生成一份架构说明和接口清单，与手写文档对比，差异处重点检查——通常差异最大的地方，就是当初设计得最含糊的地方。

用法四（写变更记录与版本说明）：设计改了一版，让 AI 基于 git diff 生成「本次设计变更说明」，供评审人快速理解改动。

核心心法：让 AI 当「第一个读者」，而不是当「作者」。它的价值在于以零背景、零耐心、零上下文的方式检验你的设计是否自洽——这恰好是设计文档最大的读者画像。

动手任务 8-A：产出你的第一份 TDD 骨架（60 分钟）
  1. 按 14 节模板创建 docs/TDD.md。
  2. 第 1–4 节认真填：版本、概述、背景与约束（最重要）、质量目标。
  3. 第 5–11 节先放你已有的产物并加引用链接，缺的地方标 【待补】。
  4. 第 12 节填第 7 章的核对矩阵结果。
  5. 第 13 节：从你的业务规则里挑 8 条，各写一句验收标准（Given-When-Then 格式最好）。
  6. 第 14 节：写下你当前最没把握的 3 个开放问题。

验收：把第 3 节（背景与约束）单独发给一个同学，问他「你觉得这个项目该用什么架构」。如果他的答案和你写的一致，说明你的约束写清楚了——如果他建议上微服务，说明你漏写了团队规模。

10

AI 时代的设计方法论

代码没人看了，那什么还有人在看？答案就是「设计」，以及「把设计变成 AI 能吃进去的规格」的能力。

本章主张

AI 让「产出代码」变得极其廉价，于是两件事同时发生：

一，代码本身贬值。「这个功能怎么实现的」不再值钱，因为十个人可以让模型各写一版。

二，「规格」的含金量暴涨。因为模型的一切产出，上限都由你给它的规格决定。你给的是「订单要能退款」，模型给你一段演示代码；你给的是带守卫条件、状态转移表、错误码和边界场景的规格，模型给你能上线的实现。

所以本课教的八个模块，在 AI 时代不是「过时的流程官僚主义」，而是最高杠杆的一步：它把「我知道要什么」变成「AI 也能确切知道要什么」。

10.3 一条铁律：AI 输出的质量上限 = 你输入的精度

这是本章最实用的一句话。给两组对照，看看你给 AI 的输入差在哪：

✗ 模糊输入

10.5 「AI 时代七条设计纪律」

  1. 一、先有约束，再问方案
    永远先写清楚团队规模、工期、预算、量级。AI 在没有约束时会给你最"先进"的方案，而这正是学生项目最不需要的。
  2. 二、让机器读得懂你的意图
    枚举值、状态名、错误码、字段名保持全仓统一并写进 OpenAPI/枚举文件。AI 对「唯一事实源」的依赖远强于对散落在文档里的描述。
  3. 三、把规格写成可验证的形式
    「状态要正确」没法验证，「CREATED + cancel → CANCELLED 并释放库存锁，且 15 分钟内不可重复释放」可以写成单元测试。规格的可验证性 = AI 产出的可验证性。
  4. 四、让 AI 做「生成」，你做「验收」
    AI 生成的每一项都要有对应的验收方式：接口 → 契约测试；状态机 → 转移表测试；SQL → 索引与执行计划检查。
  5. 五、把 AI 当第一读者，不当作者
    「它能不能看懂 / 它会卡在哪」比「它写得像不像」更能暴露设计缺陷。让 AI 演新同事、演挑刺的评审、演三个月后的自己。
  6. 六、警惕「看起来专业的错误」
    AI 特别擅长生成结构完整但缺少你业务约束的产物：五状态的标准状态机、缺 ENUM 的 DDL、漏幂等键的接口。审查重点永远是「那些只有你知道的事」。
  7. 七、人保留裁决权与责任
    AI 提的每条建议都要人裁决：采纳 / 驳回 / 暂缓，并记录理由。责任永远在签字的人身上。

10.7 一个真实的协作范式

场景3 人团队的真实工作流

  1. 周一上午：3 人一起用「卡片 1」把需求问清楚，产出「需求与约束」1 页纸。这一步绝对不能交给 AI 独自完成——业务知识只在人脑子里。
  2. 周一下午：A 用「卡片 2」帮状态机挑刺 → 3 人修状态机 → B 用 AI 生成 ER 图初稿 → 3 人核对并落 DDL。
  3. 周二：C 用「卡片 3」跑一致性核对 → 发现 7 个不一致 → 3 人分头修。
  4. 周三：TDD 整合 + 评审会（AI 记录纪要草稿，人来定结论）。
  5. 周三之后：3 人各自用「卡片 4」从契约派生实现，AI 写代码，人做验收；契约是共同基线，不互相等。

关键观察：这套流程里，AI 承担了大量「穷举」与「生成」工作，人集中在「定义、裁决、承担」上。而这恰恰是 AI 时代价值重新分配的方向——人的时间从「敲代码」转移到「想清楚」。

必须说清楚的两条红线

① 责任不能外包。代码是 AI 写的，出了线上事故，责任在你。所以「看懂并验证」是必修课——这恰恰要求你有设计能力，因为只有知道设计意图，才能判断实现对不对。

② 不要把 AI 的输出当设计。AI 生成的架构图、状态机、ER 图、OpenAPI 都是「看起来很专业的初稿」。未经人审视的设计，比没有设计更危险——因为它会让人误以为已经思考过了。AI 能帮你把设计做得更快，但不能替你做设计。

让 AI 帮你建立「个人设计能力」的三个练习

  1. 反向练习：让 AI 生成一份设计，你逐条找它的错误并说明为什么错。做 10 次，你的判断力会有质变。
  2. 对抗练习：让 AI 扮演客户/测试/新同事/运维，轮流质疑你的设计，直到你答不上来。答不上来的地方就是你设计的空洞。
  3. 约束练习：给定「1 人 / 2 周 / 零预算」，让 AI 给方案，然后你自己在 3 分钟内给出更合适的方案。反复练，直到你的约束直觉快过 AI 的建议。
动手任务 10-A：把一个模块「AI 化」（90 分钟）
  1. 挑你项目里一个中等复杂度的模块（比如订单模块）。
  2. 为它准备完整的设计输入：状态转移表、字段定义、接口契约、错误码、业务规则。
  3. 用「卡片 4」的提示词让 AI 生成实现。
  4. 逐条核对：它生成的实现与你设计输入一致吗？它做了哪些你没要求的假设？它漏掉了哪些守卫条件？
  5. 把「它做的假设」和「它漏的条件」列成清单——这份清单就是你设计文档的补充清单，补进去后再跑一次，这次它应该几乎不需要假设。

你会亲手体会到：AI 产出质量的提升曲线，和你设计输入的精度曲线，是同一条。

后台运营为管理员提供审核、投诉处理与数据看板任务审计、投诉处理、用户管理不做财务对账该有

评分要点：职责句不含「和/等/相关」等模糊词（每出现一个扣 1 分）；有「不承担的事」（2 分）；有优先级（2 分）；模块粒度一致（2 分）。

第 2 题 参考答案

推荐状态机：待接单(PUBLISHED) → 已接单(ACCEPTED) → 已取件(PICKED_UP) → 已送达(DELIVERED) → 已完成(COMPLETED)；异常态：已取消(CANCELLED)、争议中(DISPUTED)、已退款(REFUNDED)。

评分要点：状态数 ≥6（2 分）；有终态（2 分）；每条转移有守卫或明确无守卫（4 分）；有异常分支（争议/退款/超时）（4 分）；附带动作体现了业务规则（3 分）。

第 3、4 题 参考答案要点

第 3 题：异常分支应覆盖 ① 用户发完就取消 ② 无人接单超时 ③ 两人同时抢单 ④ 接单后爽约 ⑤ 取件码输错 ⑥ 快递丢失/破损 ⑦ 送达后无人确认 ⑧ 费用争议 ⑨ 支付失败 ⑩ 跑腿员恶意取消 ⑪ 押金退还失败 ⑫ 通知发送失败。

每条需包含三要素，缺项扣分。加分项：区分「用户可自愈」和「需人工介入」两类。

第 4 题：页面清单示例——首页/任务大厅、发布任务、任务详情、我的任务/我的发布、跑腿员接单页、订单状态页、钱包、后台投诉处理。线框须含错误态（网络失败、码输错）与空态（还没有任何任务）。加分项：标出某页面上每个按钮对应的状态机事件。

第 5、6 题 参考答案要点

第 5 题：约束下唯一合理答案是单体应用（分层架构），理由：1 人无法运维多服务；6 周没时间处理分布式问题；峰值 50 并发单体绰绰有余；零预算禁不起托管服务集群。

选型示例：前端原生/轻框架（熟悉度优先）· 后端 Python Flask/FastAPI 或 Node Express（选熟的）· 数据库 SQLite 或托管 MySQL 免费额度（视是否需要并发写）· 部署单机云服务器 · 监控用最便宜的日志服务。每条决策必须写出「负面后果」，如「选 SQLite → 并发写有上限，若活动日流量突增需迁移，这是已知风险」。

第 6 题：核心表：`users`、`express_orders`（快递单）、`errand_tasks`（跑腿任务）、`task_events`（状态流水）、`payments`、`disputes`。

快照字段示例：`errand_tasks.pickup_code_snapshot`（下单时的取件码，若快递员后来改码需留痕）、`errand_tasks.fee_snapshot`（下单时算好的费用，后续调价不影响已下单任务）。

DDL 关键点：金额用 DECIMAL(10,2)；状态用 ENUM 或 VARCHAR + CHECK；任务号 UNIQUE；idx_runner_status 支撑接单池查询；每张表有 created_at/updated_at。

第 7、8 题 参考答案要点

第 7 题：6 个接口示例——POST /tasks（发布）、GET /tasks（任务大厅）、GET /tasks/{id}、POST /tasks/{id}/accept（抢单）、POST /tasks/{id}/pickup、POST /tasks/{id}/confirm、POST /disputes。

需幂等键：发布任务、抢单、确认收货（防止重复提交产生重复订单/重复结算）。错误码示例：TASK_NOT_FOUND、TASK_ALREADY_ACCEPTED、TASK_STATE_CONFLICT、CODE_MISMATCH、PAYMENT_FAILED、NOT_TASK_RUNNER、DISPUTE_NOT_ALLOWED、IDEMPOTENCY_KEY_REUSED、INVALID_STATE_TRANSITION。

第 8 题：评分只看是否认真做了核对并给出修改动作，不要求答案唯一。典型不一致：状态机有「争议中」但表里没有对应 ENUM 值；页面有「我要投诉」按钮但没有 disputes 表和接口；任务大厅要按「距离最近」排序但接口没有位置参数；架构图没画对象存储但代码要存取件码图片；错误码在两个模块各写一套。

Blocker 判定示例：「状态机有争议中但 DB ENUM 缺值」→ 定时任务扫描到该状态时写入即失败，整条线跑不通；「页面有按钮但无接口」→ 核心链路断掉。两者都属 Blocker，因为「不改就做不下去」。

第 9 题 参考答案（开放题）

四条以上理由，任选即可得分：

  1. AI 的输出质量上限由输入精度决定。不说清状态、守卫、错误码、幂等，AI 只能给演示代码——这正是本课八章在训练的能力。
  2. 业务知识只在人脑子里。「48 小时内可退款」「交接码校验」这些约束不是通用知识，AI 不知道，除非你写下来。而写下来就是设计。
  3. 跨产物矛盾 AI 不会自动消除。模型看到状态机和 DDL 不一致时，会「选择一个继续」，而不是停下来问你——除非你要求它报告矛盾。
  4. 验收需要判据。没有设计就没有「什么算对」，AI 写完你也不知道怎么验，只能靠看起来对。
  5. 责任不可外包。事故责任在签字的人身上，而判断 AI 实现对错的能力来自设计能力。

最小协作流程（四步）：① 人定义问题与约束 → ② 人产出可验证规格（状态机/契约/错误码） → ③ AI 从规格派生实现并报告假设 → ④ 人核对假设与产出，补回设计。

13.3 一份最小起步清单

如果你时间紧、只想先做起来，按这个顺序，每项控制在半天以内：

  1. 写出约束（30 分钟）
    团队几人、多久、多少钱、多少人用、什么端。写在 docs/CONSTRAINTS.md。
  2. 列功能模块（1 小时）
    8 个以内，每个一句话职责 + 不承担的事。写进 docs/MODULES.md。
  3. 画核心对象状态机（2 小时）
    只画最重要的那一个对象（通常是订单）。必须写转移表。docs/STATE.md
  4. 定 6 个接口（2 小时）
    路径、方法、字段、状态码、统一错误结构。docs/api/openapi.yaml
  5. 写 DDL（2 小时）
    5–8 张表，含主键、外键、唯一约束、索引。docs/db/schema.sql
  6. 跑一次核对（1 小时）
    按 C1–C10 过一遍，必出结论。docs/CONSISTENCY.md
  7. 用 AI 实现一个模块（半天）
    用卡片 4 的提示词从契约派生实现，然后逐条核对它做的假设，补进设计。

结语

这门课真正想教你的不是八个模板，而是一种把模糊变精确的习惯。

需求是模糊的，设计是把模糊收敛的过程；而今天，AI 会以极高的速度忠实地实现你给出的任何东西——无论它是清晰的还是含糊的。所以，把事情想清楚这件事，从来没有像今天这样值钱。

先想清楚，再动手；先定义，再生成。
